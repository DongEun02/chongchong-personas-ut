### 집계 대상·분모와 계산 방식

| 지표 | 집계 대상·분모 | 처리 |
| --- | --- | --- |

| 평균 AI 자기보고 용이성 | 각 TASK 유효 30건, 모두 응답 | 점수 합 146 / 136 / 87을 각각 30으로 나눔. 1=매우 어려움, 5=매우 쉬움 |
| 결측·대기 | 결측은 0으로 대체하지 않음 | 본집계 시간·행동·불필요 행동·용이성은 90/90 존재. 모델·도구 대기는 90/90 `null`로 분리 측정 불가 |

- 결과 90개와 대응 행동 로그 90개의 runId를 대조했다. 서로 다른 runId 90개이며 결과↔행동 로그 ID 불일치는 없었다. TASK×페르소나별 1건이고 실행 시각·행동 타임스탬프·관찰 상태를 비교하여 복제 결과로 볼 동일 내용 묶음도 발견하지 못했다. 경로가 같다는 이유로 중복 처리하지 않았다.
- 90건 모두 행동 배열 길이와 `actionCount`, 불필요 표시 수와 `unnecessaryActionCount`가 일치한다. 시작·종료 시각 차이와 `elapsedMs`, 각 행동 시각과 `elapsedFromStartMs`도 일치한다. 이것은 기록의 내부 정합성 점검이며 실제 서비스 상태의 재검증은 아니다.
- 실행 당시 적용 규칙은 `promptDelivered`, `taskSpecific`, 행동·검증 메모를 함께 읽었다. 일반 설계인 [tasks.md](../tasks.md)와 [README.md](../README.md)를 실행 결과로 간주하지 않았다. 구체적인 차이는 2장·5장에 적었다.
- 실제 실행일은 저장된 UTC 시각을 KST로 환산하면 2026-11-05다. 전부 `version=current`, `serviceCommit=null`이다. 폴더명 ‘개선 전’만으로 고정 A 버전이나 개선 전후 효과를 확정할 수 없다.

### 시간과 행동의 경계

T01·T02는 준비된 시작 화면의 관찰·시작 캡처 뒤 타이머를 시작하고 목표 완료 관찰에서 끝내는 실행 규칙이다. 관찰·준비·사후 캡처·용이성 질문은 행동 수에서 제외했다. README의 일반 규약에 있는 명시적 관찰 요청·최종 답변까지 모두 세는 방식으로 소급 통일하지 않았다. T04는 `actions.json`의 과업 행동과 `taskSpecific.cleanupActions`의 종료 후 정리를 구분했다. 로그인·시작 상태 복원·잠금 대기는 과업 시간에 추가하지 않았다.

T04 P09의 준비 잠금 대기는 211,689ms(211.689초), P08은 9ms로 별도 기록되어 있다. 이를 과업 시간 58.067초·54.010초에 더하지 않았다. 다른 실행의 미기록 잠금 대기를 0으로 추정하지 않았다. `externalWaitMs=0`은 90건에 저장된 값이며, 새 멤버 가입을 실제로 기다리는 전체 흐름을 수행했다는 뜻이 아니다. 모델·도구 대기는 경과 시간에 포함되지만 분리값은 알 수 없다. 근거: [T04 P09](<../runs/개선 전/T04/current/P09/result.json>), [T04 P08](<../runs/개선 전/T04/current/P08/result.json>).

### T04 — 신규 멤버의 과제 수행·제출 대상 포함(새 기준)

**실제 목표:** “새로 가입한 이재윤님도 이미 만들어진 ‘마감 기한 임박한 과제1’의 내용을 수행하고 제출할 수 있게 해주세요.” 일반 설계의 ‘과제 생성→초대 전달→가입 대기→기존 ID에 추가’ 전체 흐름을 이번 30건이 수행한 것은 아니다.

**시작 상태:** UT 테스트 스터디78의 원본 과제86 현황에서 기존 대상 1명, 신규 멤버는 스터디에 가입되어 있으나 원본 대상에는 없는 상태를 준비했다. 운영자 역할로 공유 리드 계정을 사용했다. 원본을 저장·변경하지 않고 실행별 새 과제를 생성한 뒤 종료 후 해당 생성물을 정리했다. 초기 상태 확인은 `setupAttempts`, 정리는 `cleanupActions`에 분리되어 있다. ## 6. 실험의 한계

- **실제 사용자 UT가 아닌 합성 페르소나 AI 시뮬레이션이다.** 30개 페르소나의 원문 차이가 인간 30명의 인지·경험·신체적 제약이나 만족도 차이를 재현했다는 근거는 없다. 연령·직업 집단별 대표성이나 접근성 차이로 일반화하지 않는다.
- 90건 모두 기록 모델은 `openai-codex/gpt-6.1-sol`이다. 동일 모델·공유 로그인 계정·공유 쿠키를 사용했다. T01·T02는 지정 역할이 멤버이나 실제 계정은 리드였으며, T04도 페르소나별 독립 계정이 아닌 공유 리드 화면에서 운영자 목표를 수행했다. 권한 차이·역할 불일치를 실제 멤버 UX 검증으로 해석하지 않는다.
- **AI 경과 시간은 인간의 사용 시간이 아니다.** 모델·도구 대기와 T01·T02의 동시 실행 자원 경합이 포함되고 분리 측정값은 없다. TASK 목표·시작 깊이·데이터 변경 난도가 달라 시간만으로 TASK 사용성 순위를 매기지 않는다.
- **신규 멤버 계정으로 실제 제출까지 검증하지 않았다.** T04 성공25건은 리드 UI에서 포함을 확인한 새 기준 판정이다. 실제 신규 계정의 로그인·접근·작성·제출 완료 또는 제출물 보존의 종단 검증 결과가 아니다. 일반 T04 설계의 초대·가입 대기 전체도 본집계에 포함되지 않는다.
- T04는 초기2분 지시와60초 기준 변경, P03의 사후 통지, P26의 제한 이후 조작이 존재한다. 본판정은60초로 일관되게 재계산했지만 모든 실행이 사전에 동일 시간 안내를 받았다고 볼 수 없다. 실패5건을 사용자 오류나 기능 장애로 단정하지 않는다.
- T01은 단일 스터디·두 과제·정답1건이다. 복수 스터디, 대규모 목록, 시간 경계, 비대상자·미제출 혼동 조건을 포괄하지 않는다. 정답표는 검증 메모에 언급되지만 독립된 구조화 파일로 보존되어 있지 않다. 부분 발견량·재현율·정밀도 같은 설계상 추가 지표를 임의 생성하지 않았다.
- T02 목록의 복수 카드 표시는 확인되지만 계정의 전체 가입 정답 목록은 구조화되어 있지 않고 대표 캡처는 스크롤 화면 일부다. 표시된 카드와 실제 회원 데이터의 독립 대조까지 재검증한 것은 아니다.
- T04의 원본 보존은 28건에서 종료 후 원본 명단 직접 재열람 대신 목록의 원본 제목·0/1 제출 유지와 원본 저장을 하지 않았다는 기록에 주로 의존한다. `originalAssigneesAfter=null`을 빈 명단이나 보존 실패로 바꾸지 않았다. 생성물은 측정 뒤 정리되었으므로 현재 서비스 상태를 확인하는 보고서가 아니다.
- `version=current`·제품 커밋 미기록이므로 개선 전후 인과 효과를 계산할 수 없다. repeat=3/4는 현재 코호트의 저장 라벨이며 같은 TASK의 반복 표본 여러 회가 현재 있는 것은 아니다. 결측 과거 실행을 복원하거나 표본 수를 늘리지 않았다.
- 시작 캡처를 만들었다는 실행 메모는 있지만 현재 각 디렉터리에는 `final.png`만 있다. 원본에 없는 시작 캡처·도구 완료 시각·신규 계정 증거를 만들거나 추정하지 않았다. 본 문서의 개선 제안은 이러한 증거 범위 안의 가설이다.
